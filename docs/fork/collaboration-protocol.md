# Collate collaboration protocol

An invitation grants room access to anyone who presents it. It identifies the iroh host endpoint, a randomly generated bearer credential and connection data. Transport uses iroh QUIC with ALPN `parabol/codesign-peers/1`. Collate's invitation namespace keeps the wire separated from Repro With Friends. Display names are labels. The authenticated iroh public endpoint key provides actor identity.

Control and edit messages use bounded JSON packets with a protocol version and message type. Large artwork travels in ordered binary packets on the authenticated peer connection. The guest can request the immutable seed in ordered blocks. It verifies the length and SHA-256 and validates the normalized DesignCraft document before opening a fresh tab. A guest with a seed already open skips the download. The guest then sends the hashed seed and last revision. After validation the host sends ordered commits and a catch-up marker. Presence is ephemeral and separate from the journal. It includes a spread-local pointer and a bounded set of stable selected object IDs.

A proposal carries an actor-local sequence, a base revision and a bounded typed batch. The room derives the author from the authenticated connection. It validates any new shared IDs against the actor and sequence, rejects unknown targets or unsupported operations, and verifies property conflicts against changes made after the base. Shared objects get stable IDs independent of the peer's native numeric allocation. Host-confirmed commits receive contiguous revisions and replay idempotently. Retrying an already accepted actor and sequence returns its original commit. Later proposals from other actors can change disjoint properties. A stale competing edit to the same property is declined, and the guest retains the last confirmed document.

Comments are operations in the same stream. Their anchors reference a stable page or object ID, or the original text atom IDs in a selected range of one story. The range spans its first and last surviving original atom. A removed page, object or story leaves its thread visible as **Anchor removed**, as does a text range whose original atoms are all gone. Undo can restore a text anchor. Authors remain identified by their actor key when a display name is unavailable. Undo and redo are new host-confirmed compensations for the requesting author's eligible edits. They preserve independent changes and are refused if another actor has since modified the same target.

Simple stories use stable Unicode scalar IDs. An insertion names the preceding ID, including a deleted character kept as an insertion anchor. Delete and character-format requests target the IDs that were in the local selection, so they leave concurrent insertions intact. Paragraph-format requests address the start of the story or the preceding newline. Each paragraph can use an existing style and local overrides for alignment, indents, spacing, hyphenation, language and rag settings. Paragraph language sets the dictionary inherited by its text. The rag pattern, short-line inset, four line insets and near-flush threshold are independent writes. Distances travel in points, and the four insets travel together as one pattern. The host orders competing inserts and edits to the same formatting attribute. Independent formatting attributes combine. A new paragraph copies the preceding paragraph's format at the time of insertion. When a newline is deleted, the merged paragraph keeps the first paragraph's format. Writes to the hidden paragraph become visible again if its newline is restored. Stories with advanced overrides, linked text, tables or embedded markers remain outside shared editing.

Undo and redo toggle the original author's text batch in its surviving story. The host derives that toggle from the confirmed history. Other peers and journal replay verify that it matches the author's expected correction. Inserted atoms keep their positions as anchors while hidden. Undoing a deletion leaves a character hidden if another active deletion still covers it. Formatting keeps its original rank, so redoing an older write leaves a later active write in effect. A retained story's text history survives page repagination.

Creating a text frame or converting an unassigned frame creates a simple story. The host's ordered commit gives the frame a canonical story ID. The creator remembers the caret locally, resolves it by the stable frame ID, and sends buffered typing after confirmation. A declined proposal or a changed selection leaves buffered text available to copy. The caret and buffered text stay local until submitted as a text edit.

A text-frame deletion removes one unthreaded frame and its simple, unreferenced story. It leaves its comment threads orphaned and conflicts with text edits to that story. When deletion commits first, the rejected author can copy submitted insertions and any queued text. When a text edit commits first, the host declines a stale deletion. Text-frame deletion is a standalone structural proposal.

The protocol limits each application packet to 48 KiB, the document model to 4 MiB and room history to 1,024 transactions or 8 MiB, whichever comes first. The adapter applies at most 64 operations per transaction. Long-running rooms currently need a new seed after reaching the history limit.

Page edits are standalone structural proposals. Insertion names the next page's stable ID or the end of the document, the parent spread, and the expected allocator. Removal names stable page IDs. Native repagination replaces spread IDs, so the host rejects requests that compete with a stale page edit. Validation preserves the ordering and placement of remaining content and refuses changes to existing bookmark or link targets. Removed frames follow the normal frame-deletion restrictions. Page and object comments survive as orphaned threads. Earlier trailing-page operations remain readable in encrypted journals.

The host allocates every new layer in commit order. A creation names the layer it belongs before, so concurrent drafts with the same provisional ID receive distinct confirmed IDs. Layer settings, stack order and removal replay as single structural proposals with at most 256 target layers. Setting different layers can commute. The host declines stale content edits that cross settings or removal. It checks guides, nested and anchored content, and frame references before removing a layer. Ordinary unreferenced frames can be deleted with their layer, while a merge moves supported content without changing frame IDs. Comments on deleted frames stay visible as orphaned threads. Active layers stay local to each editor. The author can select the new layer when it is confirmed unless the author switched to another layer while waiting. When a layer is removed, peers using it fall back to their document's working layer.

The seed fingerprint covers normalized document metadata and the SHA-256 digest of each embedded asset and proxy. When the seed artwork exceeds 2 MiB, a manifest identifies the binary attachments by digest and length. Live placements larger than 2 MiB also carry references in the edit metadata. Small placements retain their inline representation. Large JSON edit messages use ordered 24 KiB fragments.

Binary packets carry the digest, total length and byte offset. Each recipient stages the ordered bytes in a temporary file, verifies the complete digest and checks the format and decoder limits before admitting new artwork. A slow receiver can apply backpressure. The guest that placed an image can confirm the host’s receipt against its pending edit and reuse its own bytes. If the pending edit is missing or differs, it requests the full revision and artwork again. A late guest receives the seed and then the artwork needed for subsequent revisions. The document includes the filename and embedded data. Paths to the sender’s original files stay local.

The room allows 1 GiB of retained artwork, including the seed. Edits must also fit the existing metadata and history limits. Raster images have a 12,000-pixel side limit and a 16,777,216-pixel area limit. A room PDF can be up to 512 MiB, with up to 128 pages and 16,384 parsed objects. The selected page and crop travel separately, so a new placement of the same PDF can reuse the original bytes. Admission checks encryption, decoded streams, page dimensions and embedded raster images.

All participants, including an unattended room server, need protocol version 14. Earlier journal formats remain readable. On macOS, the encrypted recovery journal stores large artwork in authenticated chunks and refers to it by digest. The [standalone server](room-server.md) uses a private room directory and writes the artwork and revision before confirming an edit.

An encrypted recovery record belongs to the saved document's path. Save downloaded room documents to enable recovery. Use **Save a Copy** to create a standalone snapshot at another path without moving the active room's recovery record.
